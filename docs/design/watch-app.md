# Watch app: requirements

Status: WATCH-101 to WATCH-108 are built (WATCH-106's alerts are unit-tested, not yet run in the simulator or on a watch) (a run saves to Health with its route; the real-watch check is deferred until a watch is available). WATCH-109 onwards are open: see `TODO.md`.

## Why

The Workout app on the Apple Watch cannot use the athlete's own heart-rate zones. This app is a small watchOS app that records a workout with `HKWorkoutSession` and `HKLiveWorkoutBuilder` (so it saves a normal `HKWorkout` to Health) and coaches the run with TrainingApp's own zones.

## Scope

**v1**

- Platform: watchOS 26 minimum, matching the iOS 26 target.
- Activity: outdoor running only.
- Order of work: planned workouts first, free recording second.
- Fully standalone during a run: today's plan and the zones are cached on the watch, the run is saved on the watch, and it syncs later. A dropped phone link must not affect a run.
- The existing `WatchSchedulePlanner` / `WatchScheduleSync` path to the Workout app stays. The new app is an alternative.

**Later (not v1)**

- Several workout pages, configurable from the iOS app (which pages, and which metrics each holds).
- A map page, with workout metrics on it.
- Other activity types (cycling, swimming, strength): WATCH-126. Free recording of a run with no plan is built (WATCH-108).

## Data in

- **HR zones** are owned by TrainingApp and synced to the watch (mechanism open, see below). The watch looks up bpm bounds from them.
- **Planned workout** for today (and a few days ahead) is synced to the watch. Step targets are a **zone number (1 to 5)**, resolved to bpm on the watch from the synced zones. This matches the zone-position model of MVP5-148.

## Workout screen (v1)

One fixed page showing:

- total elapsed time
- time remaining in the step, or distance remaining, depending on the step's end condition
- the step's target, shown to suit its type (zone with the current bpm and a colour band)

**As built (WATCH-105, replaced by WATCH-128):** the step metrics page of WATCH-105 (`RunMetricsPage`: step place, a big countdown, a progress bar, a heart-rate gauge) was removed from the run pages in WATCH-128, and its file deleted. What is left of it is described here as the history of the screen; what runs now is under **Run pages (WATCH-128)** below.

- **In a planned workout**, from the top: the step's place, kind, goal and target ("4/14 20 s Z4"); what is left of the step as the big number (a clock, or the distance left, or "Open" for a step that waits for the lap button); a bar for how far through the step the run is; the step's heart-rate target as a name and bpm range ("Z4 163-177") over a gauge, with the target band in green and a marker for the current heart rate; the heart rate itself, coloured blue below the target, green in it and red above it, with the words next to it ("10 bpm above", "In target") so the colour isn't the only signal; the total time and the distance, small; and the next step ("Next: Recovery 20 s Z2", "Last step"), or "Paused".
- **Target forms:** a whole zone, a stretch of zones (positions, such as 4.0-4.5) and a bpm range all resolve to bpm on the watch (`StepHeartRateTarget`, tested). A pace, power or RPE step with no heart-rate target, or a zone target with no zones yet, shows the zone the heart rate is in instead.
- **In a free run**, and after the last step ("Workout done"): the total time as the big number, the zone the heart rate is in, the heart rate and the distance.
- **Controls page:** next step (or lap), pause and resume, and end with a confirmation. The simulator's debug lines (fixes, location, events) are at the bottom of this page. It is one swipe to the side of the data screens.

**Run pages (WATCH-128; the data screens come from a `RunScreenSet` since WATCH-131, see "Configurable screens").** The run is a horizontal pair of pages, the controls and the data screens, and the data screens are a **vertical stack the Digital Crown turns through** (`.verticalPage`; a scroll over the crown in the simulator, which is not a drag or a click): the **standard metrics screen** (`RunScreenPage`) on top and, in a planned workout, the **zone dial** under it. A free run opens on the standard screen, a planned workout on the dial; the page moves to the dial when the steps start and back to the standard screen when the last one ends. Whether the crown turns the pages on a real watch is not checked (WATCH-121).
- **Standard screen:** rows from the bottom up, each a value with its unit or caption: total time (yellow), distance ("1.21 KM"), heart rate with `ZONE 2.3` at the trailing edge (both blue under the step's heart-rate target, red over it, white in it or with no target), current pace (`9'24"` with "CURRENT PACE") and average pace. It takes a list of `RunMetric`, bottom-aligned, so fewer metrics stay at the bottom (WATCH-109). "Workout done" in green after the last step.
- **Shared style:** `RunMetricStyle` holds the fonts and spacing of both screens (values 30 pt rounded, units and "ZONE" 17 pt, captions 12 pt, 3 pt between rows on top of the values' trimmed line height). Meant to fit six rows on an Ultra and five on other watches (worked out from the screen heights, not checked on a watch).
- **Pause:** a paused run shows an orange "PAUSED" at the top left of every data screen (`RunPages`) and VoiceOver says it.
- **Pace** (`PaceWindow`, `PaceText`, tested): the current pace is over the last 20 s of workout time and ends at the last distance reading while that is under 3 s old (distance arrives in jumps, so measuring to the clock made it swing), then at the clock, so a stop shows as a slowing pace and then "--"; under 0.3 m/s or in the first 5 s it is "--". The average pace is the last reading's distance over the time it was read at, "--" under 50 m. Per kilometre, or per mile in the US and the UK.
- **The dial** keeps what the removed page told: no line for the next step (removed 2026-11-25, it was not asked for); for an open step only, a line above the countdown, "Press Next step to move on"; no debug line (the simulator's alert log was taken off the dial 2026-11-25, it was not asked for).
- The gauge and the colours show only where the heart rate is against the target right now. When to alert is `ZoneAlertEngine` (WATCH-106, see Alerts below).

Controls: pause and resume, and a manual lap button. Steps **auto-advance** on their time or distance end condition, and the lap button also moves on manually.

## Target zone dial (WATCH-118)

A second run screen for a planned workout, drawn by the user in FreeForm (2026-11-23; the drawing was white on black the wrong way round, so the real screen is white text on black): a bar with all the zones on one line shows where the heart rate is against the **target zone**.

- **Views:** since WATCH-132 the dial is the default workout screen "dial" of a `RunScreenSet`, drawn by `RunScreenPage` from its items: the step countdown widget (`StepCountdownRow`), the heart-rate and total-time metrics, the zone bar widget (`ZoneDialBar`, in `TrainingWatchKit`) and the battery widget (`BatteryRow`: the line and the bar, with the forecast). `ZoneDialPage`, `ZoneDialHeartRate` and `ZoneDialTotalTime` are gone (the metrics' rows look the same); each widget has its own VoiceOver label instead of the dial's one sentence. The countdown and the battery views are now `StepCountdownRow` and `BatteryRow`.
- **Bar:** all the zones on **one horizontal line** (`ZoneDialBar`) in their own order, zone 0 (below zone 1, grey) on the left to zone 5 on the right, so a rising heart rate moves to the right. **Every zone is the same size except the target zone, which is three times as wide** and drawn **bright** and taller; the others are a **darker** shade of their zone's colour (the shared `HeartRateZone.zoneColor`). The target is therefore a bit to the left of the middle for a low target zone and to the right of it for a high one. **When the target zone changes, the line is laid out again** and the zones glide to their new places (`ZoneDial.spans(target:length:)` blends two layouts). Earlier versions drew a ring round the screen (a rounded rectangle open at the bottom, one with a gap for the clock, then a circle) and then a line with the target always in the middle and the lower zones squeezed to its left; none of them gave a clear picture.
- **Triangles:** a small one above the bar pointing down and one under it pointing up, both at the heart rate's position along the zones (`ZoneBands.position(forHeartRate:)`: 2.5 is halfway through zone 2, zone 0 spans one zone 1 width below zone 1, above zone 5 it stays at the right end). In its zone's stretch it is by how far through the zone the heart rate is. The geometry is `ZoneDial`.
- **Text,** top to bottom, the values to the **left** and the interval to the **right**: the step's **countdown** (time or distance left; "Open" for an open step) in white, with a two-line caption beside it ("REMAINING" over "STEP TIME" or "STEP DISTANCE"; none for an open step) and, at the right, **which interval or step it is** as x/y in the primary colour, with a small "REP" before it in a repeat ("REP 5/12" for the fifth of a block repeated 12 times, otherwise the step's place among all the steps, "2/6", so every step has a number: `ZoneDialText.placeFraction`); the bpm with its "BPM" at the **left** and the heart rate's place as "ZONE 2.3" at the **right**, both values in the state's colour; the bar; the **total workout time** in yellow (yellow is the total time on every screen); and the battery. The fonts and sizes are shared with the standard metrics screen (`RunMetricStyle`: values 30 pt rounded, units and "ZONE" 17 pt, captions 12 pt), and so is the gap between rows (3 pt, on top of the values' trimmed line height). The rows sit together at the **bottom** of the screen and need not fill it. The watch's own clock at the top right can't be hidden without private API, so the content keeps at least 34 pt free at the top (`contentTop`, a guess to check on a watch). Since WATCH-132 each item has its own VoiceOver label, so the colours' meaning is spoken: the heart-rate zone bar says whether the heart rate is below, in or above the target, the battery says its charge and forecast, and the step item says the time left and which step it is.
- **Colour:** the zone's value and the bpm are **white** in the target (and when the step has no target), **blue below** it and **red above** it, so a glance says whether to speed up or slow down. The "Zone" and the "BPM" are always in the secondary colour. The background stays black. The state has a margin of a tenth of the target's width, at least 1 bpm, beyond a bound before it changes, so a heart rate on a bound doesn't flicker the colour. (An earlier version coloured the whole background dark blue or dark red; the colour is on the text now.)
- **A target that is part of a zone** (such as Z4.0-4.5 or 150-160 bpm): the whole target zone is in the darker shade, and only the target's stretch of it is bright, so the bar agrees with the colour and the alerts.
- **A step with no heart-rate target** (a pace, power or RPE step, or no zones yet) has no zone for the top: the bar keeps zone 3 as the target there, with no zone bright and only the triangle moving, so it doesn't re-lay itself at every zone boundary.
- **Where:** the zone dial is under the standard screen in the crown stack of a planned workout, and the screen the workout opens on; a free run has the standard screen only. A choice of screens is WATCH-109. The stack moves to the dial when the steps start and back to the standard screen when the last one ends, but only if it is on the screen that is going away.
- **Battery:** at the very bottom, just under the total time: "BATTERY 87%" in 12 pt type and the secondary colour, with the forecast at the right of the same line, and under it a **bar** (watchOS has no battery indicator of its own in an app, as it has the clock). The bar has ten parts with a small gap every 10%, filled up to the charge (a part of the one it falls in) and in a dim grey beyond. It is kept above the run's page indicator at the bottom (22 pt, a guess; the page's own safe area keeps about 40 pt free there, which the content ignores) and in from the sides, since the screen's corners are rounded (a bar along the very top lost its ends, which is why it is at the bottom). `BatteryDisplay` and `BatteryBar` are in `TrainingWatchKit` (the logic is tested); the level is read from `WKInterfaceDevice` once a second with the dial's timeline, since watchOS has no notification for it. This only shows the battery; warning about it and handing the run to the phone are WATCH-110 and WATCH-111.
- **Battery forecast (WATCH-119):** in a planned workout the line reads "BATTERY 67%" at the left and "~44% AT END" at the right, and the bar is coloured by what that end charge means, instead of by the charge now: **green** (at least 20% left, after a 3% margin), **yellow** (10% up to 20%), **orange** (under 10%, still above 0) and **red** when the battery will run out before the end, which says "EMPTY IN 0:42" instead. `BatteryForecast` (`TrainingWatchKit`, tested) takes the drain per hour from the readings of the last 20 minutes (one every 30 s, taken by the step ticker) and blends it with a typical 12% an hour until the run has been measured for 15 minutes, because the level moves in coarse steps and the first minutes say little; a measurement needs 5 minutes and a 2% drop (or 15 minutes, and 15 minutes with almost no drop count as half the typical drain, not as none, since the level moves in coarse steps), and a rising level is ignored. What is left of the workout comes from `WorkoutStepEngine.remaining(progress:secondsPerMeter:)`: the rest of the current step and every step after it, time goals as they are and distance goals at the run's average pace (6:00 per km before the first 300 m). An **open step has no end**, so it is counted by how long the phone expects the whole workout to take (`WatchPlannedWorkout.typicalDuration`, the forecast from the athlete's paces that the planned cards show, sent only for a workout with an open step) less the time run, and never less than the steps known to be left; with no such figure the forecast isn't shown, and neither is it for a charging or unknown battery or a free run (those keep the colours of the charge itself: green above 20%, yellow above 10%, orange from 5%, red under 5%). VoiceOver says the forecast too. **The drain the forecast starts from** (until the run has measured its own) is learned: the watch writes the battery at the start and the end of each run into the `HKWorkout` (`WorkoutMetadata.batteryStart` and `batteryEnd`) and keeps the drain of its last 10 runs of at least 15 minutes (`BatteryDrainHistory`, in `UserDefaults`) with what it knows at the start: Low Power Mode and whether cues may sound from the speaker. The next run starts from the median of the runs with the same factors, or of all runs while fewer than two are alike, and the estimate is rated low, medium or high by the number of alike runs and how far apart they are; when it is low VoiceOver adds "a rough estimate". When the watch has no runs of its own (a new watch) it starts from the phone's figure, `WatchPlannedWorkout.drainPerHour`: the median of the last runs whose battery the phone read from the workouts (`Activity.batteryDrainPerHour` in TrainingKit, sent by `WatchPlanSync`). Not used: the outdoor temperature and the always-on display, which the watch can't read.
- **Battery warning (WATCH-110):** when the battery gets worse the watch taps the wrist and shows a **temporary warning screen over everything**, the whole screen in the battery's status colour with black text on yellow and orange and white on red: **yellow "BATTERY LOW"** (tight), **orange "BATTERY CRITICAL"** and **red "BATTERY WON'T LAST"** (the forecast says it runs out before the end) or "BATTERY NEARLY EMPTY" (under 5% with no forecast to say so), with the charge and the forecast under it ("12%  ·  ~4% AT END", "50%  ·  EMPTY IN 4:10"). It **stays until the athlete dismisses it by tapping the screen or turning the Digital Crown** (WATCH-121; it never goes by itself; the screen takes the crown itself, so the turn doesn't also switch the data screen underneath), taps the wrist again every half minute while it stays (four times at most), ignores a tap or turn in its first second (the athlete's last one, meant for what was on screen), and VoiceOver announces it and treats it as modal. Dismissing it with the Digital Crown was tried and does not work yet: a turn of the crown goes to the watch's grid of apps, also on the data screens without a warning (WATCH-121). The Action button is not used (WATCH-120): watchOS lets an app hear it only through an App Intent that the athlete assigns to the button,, which is a project of its own (much later). The level is the worse of the forecast (a planned workout) and the charge itself (20% or less is yellow, 10% or less orange, under 5% red), so a free run is warned too, and a charging battery gives none. **Each level is given once** (`BatteryWarningTracker`, tested): a level that wavers is not warned about again unless it stayed lower for two minutes. The recorder checks every 5 s, in planned workouts and free runs, and takes the half-minute readings for the forecast. The haptics are `.notification`, `.retry` and `.failure` for the three levels: starting values until WATCH-117 gives each signal its own pattern, and the sound for earbuds is WATCH-107. In the simulator the scheme starts the battery at 25% (`-batteryLevel 0.25`) and drains it at 3.0 an hour (`-batteryDrainPerHour 3.0`): yellow after about a minute (20%), orange after three (10%) and red after four (5%).
- **To tune on a real watch:** where the content starts under the clock (34 pt), the room for the page indicator (22 pt), the battery bar's height (5 pt) and its inset from the sides (10 pt on top of the content's padding), the bar's height (14 pt), the dark shade (40% opacity), the blue and red of the text, the target's width (three times the others), and the text sizes on the smaller watches.

## Configurable screens (WATCH-109, design agreed 2026-11-25, not built)

The athlete chooses in the iPhone app which data screens a run shows and what each holds.

- **Item:** a screen is a stack of **items** and each item has a **height** in units. A plain metric is height 1 (what `RunScreenPage` draws today). A widget is taller: the **zone bar** (only the HR zone blocks with the current-heart-rate indicator, what `ZoneDialBar` is) is height 2, the battery line and bar height 1. Further widgets: the step countdown (time or distance left with the interval x/y), a **heart-rate zone histogram** (time in each zone) and an **elevation graph** of the whole run (later also the part of a planned route not yet run). A **pace zone bar** comes later, with pace targets. Items sit together at the bottom, as now.
- **Capacity:** a screen holds **6 units** (an Ultra; 5 fit on the other watches, so the first item drops off there, which is why the most important item goes last). The editor refuses to add past 6 and shows the units used.
- **Metrics** are a large, searchable catalogue grouped by main metric (Heart Rate: heart rate, zone, average, median, median in the step, median over the last km, time in zone ...; Pace; Distance; Time; Elevation: altitude, climb, grade; Cadence; Lap and step; Clock, battery, ETA ...). The editor browses by group and searches. Each metric has a stable id; the first set is the five that exist (`RunMetric`).
- **Screen set:** a named, ordered list of screens, with the screen the run **opens on** (which may differ per step type, for instance the zone bar screen in work steps and the standard one in recovery; the stack still moves by itself as it does now, but by the set's choice).
- **Defaults:** one set for a **free run** and one for a **workout**. The athlete makes more and **links** a set to a workout template (a sprint interval set, a long run set); a template with none uses the workout default. The link is made from the template's editor or from the set's editor (stored once, on the template); the plan sent to the watch carries each workout's set, so the watch has what it needs offline. A step widget in a set used for a free run is simply hidden.
- **The zone dial** stops being a screen kind: the old dial is a default workout set (zone bar, countdown, heart rate, total time, battery as items). Today's standard screen is the free-run default.
- **Phone and sync:** sets are kept on the phone and sent in `WatchContext` next to zones, plan and cues (a `screens` part, `nil` = keep the last; kept in `UserDefaults` on the watch), decoded leniently (an unknown metric or widget is dropped, an empty set falls back to the default), a `WatchLayoutSync` like `WatchCueSync`. A change reaches the next run, not one that is going. Edited on the phone only.
- **Not in WATCH-109:** the map page (its own ticket: a map with one or two metrics or widgets on it) and the elevation graph with a planned route; the item model must leave room for both.
- **Built (WATCH-131):** `RunMetric`, `RunScreenItem` (a metric; height 1), `RunScreen` (6 units, items past it cut from the top), `RunScreenSet` (screens and the start screen) and `RunScreenConfig` (the free-run and the workout set) in `TrainingWatchKit`, decoded leniently and tested; a `screens` part in `WatchContext` and `WatchSyncSending.send(screens:)` (the phone doesn't send yet, that is the editor, WATCH-134); `RunScreenStore` keeps the last config in `UserDefaults`; `RunPages` draws a `RunScreenPage` per screen of the set (read when the run's pages are built; a planned workout still gets the zone dial under them, until WATCH-132). Both defaults are today's five-metric screen. The set is chosen once per run, by `RunRecorder.isPlannedRun` (known at the start, unlike the step engine) and kept in the run's pages, so a set that arrives mid-run reaches the next run. `RunScreenSelection` (tested) decides which screen shows: the set's start screen, or the dial in a planned workout, following the steps starting and ending without taking an athlete's own screen. Screen ids are unique within a set (a repeat is dropped on decode).
- **Built (WATCH-132):** `RunWidget` (zone bar, height 2; battery, 1; step countdown, 1, which needs a workout's steps; zone histogram, 2) as items next to the metrics, encoded `{kind: widget, id}` and dropped when unknown. The workout default is two screens: "standard" and "dial" (step countdown, heart rate, zone bar, total time, battery: exactly 6 units), opening on the dial. `RunScreenSelection` (tested) leaves out the screens that need steps in a run with none, moves onto the start screen when the steps begin unless the athlete has turned to a screen, and off a step screen when they are used up. The histogram has six bars, zone 0 (below zone 1) to zone 5, from `ZoneTimeTracker` (each reading gives the time since the one before to that one's zone, at most 10 s; pauses are out of the run clock). A step widget shows nothing in a free run. A screen is shown with as many of its last items as fit the watch (`RunScreen.items(fittingUnits:)`, tested): 6 units on the largest watches and 5 on the others, from the screen's height, a guess to check on a watch. The first items of a fuller screen are left out. "Workout done" shows on the first screen only. Not yet: the pace zone bar, the elevation graph, the dial's colour animation on a change of state (the heart rate's colour changes at once now).
- **Order of work:** this design; then PRs for the model and sync with the five metrics drawn from a set, the widgets (zone bar, battery, countdown, histogram), sets linked to templates, the phone editor, and the catalogue growing after it.

## Alerts

### Trigger

- Compare a **smoothed HR** (rolling average over about 5 to 10 s) with the target zone's bounds, with a hysteresis margin of a few bpm.
- An alert always fires at the **start of a step**, announcing the new target.
- When the gap to the target is larger than a zone width (for example zone 1 to a zone 5 target), stay quiet while smoothed HR is **rising fast enough** toward the target (a slope threshold in bpm per 10 s). Alert only when HR is not rising enough.
- Always alert when HR **enters** the target zone.

### Repeat

Escalating: the longer HR stays outside the target zone, the more often or the more strongly it repeats.

### Telling too high from too low

- Different haptic patterns for too low (speed up) and too high (slow down).
- A distinct confirmation cue when back in zone.
- Spoken cue ("Slow down", "Zone 3") or tones, in earbuds. **Tone and speech are two settings per kind of signal** (WATCH-107).

### One signal per meaning (added 2026-11-21)

Every kind of event gets its own haptic pattern and its own tone, so the wrist and the ears tell them apart without looking. A step change played one `.notification` haptic (and `.success` at the end of the workout), made in WATCH-104; WATCH-117 gave each of these its own, and the athlete can change them (see "As built (WATCH-117)" below):

- **Step started** (a new target): its own signal, unlike every zone alert below.
- **Too low** (below the zone) and **too high** (above it): different from each other.
- **Back in the zone**: different from both out-of-zone signals and from the step signal.
- **Far out of the zone** (well beyond the hysteresis margin, or out for long): a third, more urgent pattern, such as a short tone repeated, instead of the ordinary out-of-zone one. Above and below stay distinguishable in it too.
- The workout's last step ending keeps its own.

**Which channel (decided 2026-11-21):**
- **Headphones or earbuds connected:** zone alerts (below, above, back in, far out) are **sound only**, as a tone or speech by the WATCH-107 setting, with no haptic. That also keeps the wrist still for the heart-rate sensor.
- **No headphones:** zone alerts are **haptic only**. The watch speaker is never used.
- **Step started**, **workout done** and the battery warning follow the same rule (changed 2026-11-24, WATCH-117): several `WKHapticType` haptics play a chime of their own that can't be switched off, which sounded on top of the athlete's tone, so the automatic setting taps only when no sound plays. Haptics set to Always tap with the sound.
- Whether headphones are connected is read when an alert fires, not once at the start, so putting them in or taking them out mid-run changes the channel.

The haptic and the tone for an event are chosen together from one table (event to haptic pattern and tone), so they can't drift apart, and speech (the WATCH-107 setting) says the same thing in words. WATCH-106 decides when each event fires; WATCH-117 decides what each sounds and feels like. Haptic patterns can only be judged on a real watch, which is a few months away, so start with `WKHapticType` values that already differ clearly and tune later.

**As built (WATCH-117):** `HapticPattern` and `TonePattern` (`TrainingWatchKit`) list the nine haptics and seven tones on offer; `SignalKind.defaultHaptic` and `defaultTone` give each of the six kinds (step starts, below, above, back in, done, battery) its own. The athlete can change either per kind in the iPhone app (Alerts During a Run), kept in `CueSettings` and sent to the watch. A far alert plays its direction's signal twice, and the battery warning's levels once, twice and three times. The lap is always a click. In the same screen, Play Tone plays a tone on the phone and Feel on Watch makes the open watch app tap the haptic (a WatchConnectivity message; it needs the watch app in the foreground).

### Audio

- Announces step changes, such as "Interval 3 of 6, 4 minutes, zone 4".
- Through earbuds by default. The watch speaker is used only if the athlete turns that on.
- Pauses **podcasts** and ducks **music**. Use an audio session with `.interruptSpokenAudioAndMixWithOthers`, plus ducking for music.

The thresholds (smoothing window, hysteresis, slope threshold, escalation timing) start as proposed defaults and are tuned in real runs.

### As built (WATCH-106)

`ZoneAlertEngine` (`TrainingWatchKit`) is a pure value: `beginStep(target:at:)` at each step start and `add(_:at:)` for each reading, on the run's own clock (paused time left out). The target is a plain range and the reading is in one unit where higher means harder, so the same engine can serve heart rate (bpm) and, later, pace targets (as speed, MVP8-101). Heart rate and pace behave differently (heart rate lags the effort by tens of seconds and is smooth; pace follows it at once and is noisy, and a runner can stop or sprint within seconds), so every threshold is in a `ZoneAlertEngine.Settings` preset per signal. `RunRecorder+Alerts.swift` feeds the engine in a planned workout and `ZoneAlertHaptics` plays the haptic. `RunRecorder` lives in `TrainingWatchKit` behind `RunBackend` (session, builder, route, GPS, haptics, battery), so its phases, sums and alerts are tested with a fake; the watch app's `WatchRunBackend` is the HealthKit and CoreLocation one.

Heart rate (`Settings.heartRate`):
- Smoothed value: mean of the last 3 s. Hysteresis: a tenth of the target's width, at least 1 bpm (1.35 bpm on a 13.5 bpm zone); out of the zone at that margin beyond a bound, back in at the bound itself.
- Out-of-zone alerts wait 2 s after a step starts, so the step's own alert is heard first. The step-start alert is the old step-change haptic (`.notification`); the workout's end keeps `.success`.
- Slope rule: quiet while the heart rate moves toward the zone by at least 3 bpm per 10 s (a line over the last 10 s) and the gap is wider than the zone, or would be closed within 20 s at that speed. With too few readings to tell (under two, or less than 2 s apart), a gap wider than the zone waits for them, for 10 s at most after a step starts or a run resumes (it is usually the climb, and a watch may report only every few seconds); any other alert goes ahead.
- Entering the zone from outside gives "back in zone" (a step that starts inside the zone gives none).
- Repeats every 20 s while out, every 10 s after 60 s out; the far variant when three quarters of the zone's width (at least 5 bpm) beyond a bound, or out for 90 s. The time out of the zone keeps counting while the slope rule keeps quiet, so a long climb that stalls gets the far alert at once.

Pace (`Settings.pace`, placeholder values for MVP8-101, not tuned on any run): a wider margin, a wait of 4 s out of the target before the first alert (a lone GPS fix is not a pace), no slope rule, a 5 s grace and quicker repeats. A pace step has no alerts yet, since only heart-rate targets resolve (`StepHeartRateTarget`).

Pause and resume:
- Every pause (the button or the system) forgets the readings, in the session delegate.
- The readings after a resume are held back for one smoothing window (3 s), so a lone reading can't alert.
- Zones arriving in the middle of a step are picked up at the next reading, without an alert.

The channel (haptic or earbuds) is WATCH-107, below; the final patterns are WATCH-117. The haptics are `directionUp`, `directionDown` and `success`, the far ones twice. To see them in the simulator, use the alert test run (`-fakeAlertPlan`, see "Testing in the simulator" below): the 20 s steps of the interval track are too short for most alerts, since the first comes a few seconds into a step and the average lags. The logic has unit tests; the recorder wiring has none (WATCH-113).

### As built (WATCH-107)

`CueRouting.route(_:headphonesConnected:settings:)` (`TrainingWatchKit`, tested) turns a `RunCue` into a haptic flag and a sound. The athlete sets this in the iPhone app (Athlete ▸ Connected Services ▸ Apple Watch ▸ Alerts During a Run, `WatchCueSync`); `CueSettings` travels to the watch in the `WatchContext` with the zones and the plan, and the watch keeps the last ones in `UserDefaults` (there is no setting on the watch).

- **Where sound plays:** earbuds only (default), also the watch speaker, or off. Read when the cue fires, so earbuds put in or out mid-run change it.
- **Haptics:** automatic (a zone alert taps only when it has no sound; step start, workout done and battery always), always, or off.
- **Per kind of signal** (step starts, below zone, above zone, back in zone, workout done, battery warning): two check boxes, **tone** and **speech**, independent. Both play the tone and then the words; neither gives no sound (a zone alert is then a haptic). Far alerts follow their direction's signal. Defaults: step starts, workout done and battery have both; zone alerts are tones only, which are quicker to take in mid-effort. So "speech when the step changes, only a sound when going out of or back into the zone" is the default shape.
- **Countdown:** the *step starts* tone counts down the last 5 seconds of a step with a time goal and a step after it: one short tone a second (`RunCue.countdownTick`, checked every 0.2 s, one tone per second), and a longer tone as the next step starts. A tick is dropped rather than queued behind speech that is still playing, since a late tick is worse than none. Ticks are never a haptic and never speech.
- **Step announcements** (`StepAnnouncement`, a `RunCue.stepAnnouncement`, belongs to the *step starts* signal and plays only with its Speech on): a **work step is announced before it starts**, "Next: work for 4 minutes, zone 4", when the step before it has a time goal and the lead time (10 s by default, 5 to 30 s) is reached, so the athlete can get ready for it. A step that can't be foreseen (after an open step, a distance goal or the lap button) and every other kind (warm-up, recovery, cool-down) is announced as it starts, "Recovery, 2 minutes, zone 2". A step announced ahead is not announced again when it starts; its tone still plays then. The setting "Announce Work Steps Ahead" turns it off. Not yet different for hard work steps (zone 4 to 5) than for easy ones. A step shorter than the lead time is announced ahead right as it starts, so two announcements can follow each other. The lead time is limited to 5 to 30 s, also when the watch reads it from the phone. The step clock ticks every 0.5 s, and every 0.2 s in the last 6 s of a timed step, for the countdown.
- **Player:** `CuePlaybackQueue` (`TrainingWatchKit`, tested with a fake driver) plays the tones and words of each cue one after another, holds the audio session for 1.5 s after the last part (so a run of short tones, like the countdown, doesn't make music duck and un-duck every second) and then lets it go, so podcasts resume and music comes back up. A countdown tick is dropped while something else plays, a backlog of more than 6 parts drops further cues, and a cancel (the workout ending) stops everything and lets the session go, also in the middle of taking it. `CueAudioPlayer` (watchOS) is its driver: `AVSpeechSynthesizer`, generated sine tones, and a `.playback` session with `.interruptSpokenAudioAndMixWithOthers` and `.duckOthers`, activated asynchronously and deactivated off the main thread. The words are English with an English voice until they are localised (WATCH-123).

Tones and words are starting values (WATCH-117). Open: checking on a real watch (WATCH-122).

## Decisions (WATCH-100, 2026-11-20)

- **Sync:** both. WatchConnectivity pushes the zones and the next few days of plan instantly when the phone is reachable. CloudKit (the shared `iCloud.org.oekalegon.trainingkit.shared` container, via TrainingPersistence) is the fallback, so the watch can refresh without the phone. Add a manual refresh on the watch.
- **Plan match:** tag the `HKWorkout` metadata with the planned workout ID for an exact match. The existing time-and-type matching stays as the fallback for runs recorded in the Workout app.
- **Shared code:** the watch target uses the TrainingKit packages directly (TrainingCore, TrainingPersistence and so on). A new small package in this repo, `TrainingWatchKit` (watchOS 26 plus macOS so `swift test` works), holds the step engine, alert logic and audio cues. `TrainingAppKit` stays iOS-only.
- **Signing:** companion app `org.oekalegon.trainingapp.watchkitapp`, embedded in the iOS app, sharing its iCloud container, HealthKit entitlement and team.
- **Units and language:** follow the athlete's setting in TrainingApp, falling back to the system's. Speech uses the watch's language.
- **Auto-pause:** off in v1 (manual pause only).
- **Display, wrist down (WATCH-125, WATCH-129):** with `isLuminanceReduced` the dial and the standard metrics page redraw on the minute (`RunScreenSchedule`) instead of every second, leave out the seconds (the total time reads "0:24", a step's time left "2 min", rounded up, "<1 min" under a minute), stop animating and dim to `RunMetricStyle.dimmedOpacity`. The battery warning is reversed: a black background with the text in the warning's colour (yellow, orange or red), and the coloured background is back when the wrist is raised. Alerts rely on haptics and audio. Not checked on a real watch: that the ticks, speech and haptics still come with the wrist down (WATCH-122), and the dimming level.
- **GPS:** outdoor running configuration with an `HKWorkoutRouteBuilder`, so the route is saved. A low-power mode (reduced GPS sampling for long runs) is wanted but comes after v1.

## Zones on the watch (WATCH-102)

- The phone sends the athlete's current `HeartRateZoneSettings` (not precomputed bpm ranges), so the watch uses the same `HeartRateZoneModel` and can't disagree about a boundary, whichever zone method is set. `AppTabView` sends them through `WatchZoneSync` when the app becomes active and whenever the settings change, only when they differ from what was last sent.
- Transport is a WatchConnectivity application context (`WatchSyncChannel`): only the newest zones matter, and the system delivers the latest one when the watch app next runs. The phone holds the zones until the session is active and a watch with the app installed is paired.
- The watch keeps the last zones in `UserDefaults` (`WatchZoneStore`), so a run can start with the phone out of reach.
- The removed metrics page (WATCH-105) showed the current zone as a coloured "Z3" with its bpm range, "<Z1" below zone 1, and "No zones yet" until some arrive; the screens now show it as `ZONE 2.3` (the position along the zones, "<1" below zone 1) and `ZONE --` without zones. The colours come from one definition in `TrainingWatchKit` that the phone's charts use too. This is the raw current heart rate; only the alerts smooth it (WATCH-106).
- The CloudKit fallback for a phone that isn't reachable is WATCH-114.
- Simulator: `-fakeZones` gives the watch zones (resting 55, maximum 190) when no phone has sent any.

## Plan on the watch (WATCH-103)

- The phone reads only the plans of the next 7 days (today included) and the workouts they use, and sends the planned runs among them that have a workout and aren't completed, earliest first (`WatchPlanSync`). Only runs, because the watch app records runs; other sports stay on the Workout app's schedule. Each entry is the planned activity's ID, its date, the workout's name and its steps as TrainingKit's own `WorkoutBlock`s, so the watch reads step goals (time, distance, open) and targets exactly as the phone does. Nothing else of the phone's workout travels (library and template IDs, parameters, purpose), so the payload stays to what the watch uses.
- The zones and the plan are one WatchConnectivity context (`WatchContext`): an application context replaces the one before as a whole, so sending them separately would let each wipe the other out. A part the phone hasn't sent yet is `nil` and the watch keeps what it has; an empty plan is "nothing planned" and clears the old one. Each part is decoded on its own, so one the watch can't read (a phone updated before the watch) is left out and the other still arrives.
- Each plan carries when it was sent (`sentAt`). The phone sends again when the plan changes and at least every 6 hours while its app is used, so a plan older than 24 hours means the phone hasn't been opened: the start screen then adds "Plan from 3 days ago: open TrainingApp to update", so "No run planned today" isn't mistaken for "the phone hasn't said".
- `WatchScheduleSync` runs the plan sync at the start of each of its runs, so it follows the moments the Workout app's schedule does (the app becoming active, a plan saved, deleted or imported, a link or unlink). It doesn't follow the Athlete tab's "Send Planned Workouts to Apple Watch" switch, which is about the Workout app's schedule, and it doesn't need WorkoutKit permission.
- The watch caches the plan (`WatchPlanStore`), so a run can start with the phone out of reach. "Today" is the watch's own calendar day, so it is where the athlete is. The start screen lists today's workouts with their steps as short lines (`WatchWorkoutSummary`, for example "4 × (3 min Z4, Recovery 2 min Z2)"), or says no plan has arrived or no run is planned.
- Starting a workout with its steps, auto-advance and the live step display come with the step engine (WATCH-104, WATCH-105); until then "Start run" records a free run. Pace and power targets aren't shown (a step with a pace target shows its heart-rate companion's zone), and the run isn't tagged with the planned activity's ID yet (WATCH-104).
- Simulator: `-fakePlan` gives the watch an interval workout planned for today, `-fakeStalePlan` the same sent 3 days ago; neither is cached.

## Steps on the watch (WATCH-104)

Decisions from the scoping Q&A of 2026-11-20:

- **Starting:** each of today's workouts on the start screen is a button; tapping it starts a run with that workout's steps. "Start run" stays a free run with no steps.
- **Advancing:** `WorkoutStepEngine` (in `TrainingWatchKit`, pure logic, tested) lays the workout's blocks out as steps, each repetition of a repeated block its own step. A step with a time or distance goal ends when it is reached (time from workout time, so paused time doesn't count; distance from the run's distance); an open step waits for the lap button. The next step starts where the last goal ended, so time goals don't drift by the update interval. The recorder checks twice a second.
- **Lap button** (on the controls page, "Next step" during a workout, "Lap" otherwise): ends the current step and moves on (a press within a second of the step beginning is ignored, so a double tap doesn't skip two), and the saved workout records a lap event at that moment, so a step cut short can be told from one that ended by itself. In a free run, or after the last step, it only records a lap event.
- **After the last step** the run keeps recording as a free run until End. The step line says "Workout done" in green.
- **One haptic** at each step change, whether it came from a goal or the lap button, and a different one when the last step ends. That haptic is now the step-start alert of `ZoneAlertEngine` (WATCH-106); the zone alerts have their own haptics, and the sound is WATCH-107 (the patterns and tones are WATCH-117).
- **Saved workout:**
  - A segment `HKWorkoutEvent` per step, from when the step started to when it ended, dated by the engine's own step boundary (not when the half-second tick noticed it) and including any pause inside the step, with the step's index, kind, repetition, goal and how it ended ("goal", "lap" or "workoutEnded") in the event's metadata. A step still going when the run ends gets its segment too. Events that fail to write are kept and tried again with the next batch and just before the workout is ended.
  - A lap event for each lap-button press.
  - The `HKWorkout` is tagged with the planned activity's ID and the workout's name, so a run can be matched to its plan exactly. The keys are in `WorkoutMetadata`; they are custom, since HealthKit reserves the ones that start with "HK".
  - TrainingApp doesn't read these yet (WATCH-116): its import matches by time and type as before, and shows the events as it did for the Workout app's.
- **Screen:** (history) the metrics page showed a basic step line: the step's place ("3/6"), its text ("Recovery 4 s Z2") and what is left ("0:04 left", "9 m left", or "Press Lap to move on" for an open step). The full run screen is WATCH-105. Now the dial's step number ("2/6", or "REP 5/12" in a repeat) and next-step line say this.
- Simulator launch arguments (all in `SimulatorTestData` and `SimulatorTestHooks`; they do nothing on a real watch):
  - `-fakeZones`: the athlete's zones (resting 55, maximum 190).
  - `-fakeShortPlan`: a workout of steps a few seconds long (and a 15 m cool-down).
  - `-fakeAlertPlan` (WATCH-106): a 14-minute workout for the zone alerts: 60 s warm-up, 4 × (90 s zone 4, 90 s zone 2), 60 s cool-down (`TestWorkouts.alertTest`). Use it with `-gpxPath .../alert-test.gpx` (`make-interval-gpx.py --alert`), whose heart rate leaves the step's zone for a stretch in most steps: hard 2 goes above zone 4 and far above, hard 3 below and far below, hard 4 never gets there (155), easy 2 above zone 2, easy 3 below it, easy 4 stays above (158); the first hard and easy steps stay in their zones, as the quiet case. `AlertTestTrackTests` replays the track through `ZoneAlertEngine` and keeps the alerts it gives in step with this.
  - `-batteryDrainPerHour 3.0` (WATCH-119): drains the battery steadily from 80% (or from `-batteryLevel`) at that share of the full charge per hour, so the forecast can be seen. With the 14-minute alert workout, up to about 2.4 ends green, 2.4 to 2.9 yellow, 2.9 to 3.3 orange and more runs out; the forecast starts from a typical drain, so the colour moves as the run goes on. The scheme has 3.0 ticked, with `-batteryLevel 0.25`.
  - `-fakeDimmed` (WATCH-125, WATCH-129): shows the run screens and the battery warning as with the wrist down, since the simulator can't lower the wrist (the scheme has it unticked). Combine with `-fakeBattery` or `-batteryLevel 0.15` to see the reversed battery warning.
  - `-fakeBattery` (WATCH-118): the simulator has no battery, so the battery bar drains from 100% to 0% every two minutes of the run, through all its colours (`BatteryDisplay.simulatedLevel`); `-batteryLevel 0.15` holds one level instead (0 to 1; the scheme has it unticked). On a real watch both do nothing.
  - `-fakeIntervalPlan`: a 6-minute workout: 60 s warm-up, 6 × (20 s zone 4, 20 s zone 2), 60 s cool-down (`TestWorkouts.intervals`).
  - `-gpxPath <file>`: the GPX to play. `Tools/TestTracks/short-intervals.gpx` is a synthetic track that follows the interval workout step for step, with a heart rate that moves towards each step's level over a few seconds, so the first seconds of each hard step are still below zone 4. Some steps deliberately leave their zone, to test the alerts: the 2nd hard step goes far above zone 4 (about 188 bpm), the 4th far below it (about 140), the 6th a little below (about 158); the 3rd easy step goes below zone 2 (about 129) and the 5th above it (about 155). `Tools/make-interval-gpx.py` makes it; it is no real place. `TestWorkoutTrackTests` keeps it and the workout in step.
  - `-autostartPlan` starts today's first workout, `-autolap <after>` presses the lap button, and the simulator's debug line shows how many events were written. 
  - While one of the fake arguments is given, what a paired phone sends is ignored.
- **From Xcode** the TrainingWatch scheme (in `project.yml`) passes `-fakeZones`, `-fakeAlertPlan`, `-batteryDrainPerHour 3.0`, `-autostartPlan` and `-gpxPath $(SRCROOT)/Tools/TestTracks/alert-test.gpx`, so a run on a watch simulator starts the 4 × 90 s alert test workout on that track by itself (since WATCH-106; before it the 6 × 20 s interval run). Untick them under Product > Scheme > Edit Scheme > Run > Arguments for a normal run. For the 20 s interval run, untick `-fakeAlertPlan` and the `alert-test.gpx` path, and tick `-fakeIntervalPlan` and the `short-intervals.gpx` one. A repo path with spaces breaks the `-gpxPath` one.
- **From the command line** pass the same arguments to `xcrun simctl launch`, with the GPX's full path.

## Testing in the simulator

The simulator records no heart rate, distance or route, so debug builds for the simulator fake them (`#if targetEnvironment(simulator)` in `watchOS/Sources`):

- **Heart rate:** the GPX's own heart rate when a GPX is being played and has one, written to the workout builder at each fix; otherwise a made-up ramp from 90 to 170 bpm and back, once a second.
- **Distance:** summed from the location fixes the simulator plays back and added to the builder as one sample per batch. Each sample must stay inside the collection window (from the previous sample's end to now): a sample stamped with a fix's own timestamp can predate the builder's start, and HealthKit then puts the builder into an error state ("Unable to transition … from the Error(7) state") and the run can't be saved. The builder's own distance statistic stays near zero in the simulator even then, so simulator builds show the replayed sum instead and the distance of the saved workout in Health can't be trusted there. The screen also shows the number of fixes received.
- **Route:** the fixes go to an `HKWorkoutRouteBuilder` as on a real watch.
- **`-autostart` and `-autostartPlan`, `-autoend <seconds>`, `-autopause <after>,<for>` and `-autolap <after>` launch arguments:** start a run without tapping Start (or start today's first planned workout), end it after that many seconds, pause it after `<after>` seconds for `<for>` seconds, and press the lap button after `<after>` seconds (the Health permission sheet still needs one tap the first time).

To drive GPS from a recorded track, simulator builds play a GPX file themselves, with no `simctl location` and no location permission. The simulator shares the Mac's file system, so the app reads the file directly. Put a `.gpx` file in `~/Documents/TrainingWatchGPX/` (the first one by name is played). Nothing else to set up. (The file is read by `GPXTrack` in `TrainingWatchKit`, which has tests.) To use another file or tune the playback, set the `gpxPath`, `gpxSpeed` (default 1, the track's real speed) and `gpxStartMinute` defaults, for example as launch arguments (`-gpxPath /path/track.gpx`) or with `xcrun simctl spawn <UDID> defaults write org.oekalegon.trainingapp.watchkitapp gpxSpeed 30`.

The replay stops while the run is paused. A `gpxSpeed` (or other) default set earlier overrides these defaults until it is deleted with `defaults delete org.oekalegon.trainingapp.watchkitapp gpxSpeed`. Empty the folder (and delete any `gpxPath` default) to use CoreLocation again. The heart rate is played only by this in-app replay; `Tools/replay-gpx.py` drives CoreLocation through `simctl`, which has no heart rate, so with it the made-up ramp is what the watch shows. The debug line on the metrics page then reads `location GPX replay`. The older `Tools/replay-gpx.py` still works for driving CoreLocation through `simctl location`; run it once with `--prime` before starting the run and pass `--device <UDID>`. Keep GPX files out of the repo: they hold real locations. Build for the simulator with ad-hoc signing (`CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO`), not `CODE_SIGNING_ALLOWED=NO`, or the HealthKit entitlement is missing and the app shows "Missing com.apple.developer.healthkit entitlement".
